1. CONTEXTO DO SISTEMA
════════════════════════════════════════════════════════════════════════

O sistema classifica chips pelo Part Number (PN) digitado pelo operador.
O motor (engine.py) segue esta hierarquia:

  Camada 1 → Busca exata no banco (KnownPart status="enriched")
  Camada 2 → Gramática da família (ChipFamily + DecodeMap)
  Camada 3 → Gemini (LLM) como fallback
  Camada 4 → Fuzzy suggestions (última opção)

A nossa tarefa é sempre alimentar as Camadas 1 e 2, tornando o sistema
independente de IA para os chips que aparecem na esteira.

Arquivos relevantes no projeto
(/Users/raphaelsilvabastos/Documents/WhatTheChip/chipdocs/):

  chips/management/commands/populate_samsung.py  ← modelo a seguir
  chips/management/commands/fix_known_parts.py   ← exceções pontuais
  chips/models.py                                ← ChipFamily, DecodeMap, KnownPart, Brand

2. PADRÃO DE IMPLEMENTAÇÃO (leia populate_samsung.py como referência)
════════════════════════════════════════════════════════════════════════

Cada fabricante ganha um arquivo populate_<marca>.py. Ele registra:

  A) Brand — marca no banco (get_or_create)

  B) DecodeMap — tabelas de decodificação de capacidade/geração
     Cada linha é uma tupla (char_key, val_primary, val_secondary):
       char_key    = 1-2 chars extraídos de posição fixa do PN
       val_primary = capacidade principal (ex: "32GB", "2GB")
       val_secondary = contexto técnico (ex: densidade Gb, comentário)

  C) ChipFamily — família/prefixo com metadados:
       prefix          = prefixo do PN (ex: "THGBM")
       chip_type       = "eMMC", "UFS", "eMCP", "LPDDR4X" etc.
       subtype         = descrição curta (ex: "eMMC 5.1 Mobile")
       interface       = "eMMC 5.1", "UFS 3.1" etc.
       pn_length       = comprimento total esperado do PN
       is_emcp         = True se é Multi-Chip Package (eMMC+RAM combinados)
       active          = True
       priority        = número (menor = maior prioridade; 40 é padrão)
       decode_gen_pos  = posição no PN para extrair chave de geração (None se não usado)
       decode_gen_map  = nome do DecodeMap de geração (string vazia se não usado)
       decode_cap_pos  = posição no PN para extrair chave de capacidade
       decode_cap_len  = comprimento da chave de capacidade (1 ou 2)
       decode_cap_map  = nome do DecodeMap de capacidade
       tip             = texto de orientação para o operador (destino, avisos OCR etc.)

REGRA CRÍTICA DE CONFIANÇA: só adicionamos ao decode_map entradas
confirmadas por fonte primária ou secundária forte:
  ✓ Tier 1: Kioxia/Toshiba oficial (kioxia.com, toshiba.semicon-storage.com)
  ✓ Tier 2: Octopart, Mouser, Digi-Key (com especificação de produto)
  ✓ Tier 3: B2B verificado (Preduo, Win Source, ssfkg, samsungparts)
  ⚠ Tier 4: Alibaba/distribuidores genéricos (marcar como estimado)
  ✗ Nunca: IA sem verificação, catálogos asiáticos anônimos

3. TOSHIBA / KIOXIA — O QUE SABEMOS E O QUE PRECISAMOS DESCOBRIR
════════════════════════════════════════════════════════════════════════

CONTEXTO DA MARCA:
  • Toshiba Memory Corporation foi criada em 2017 como spin-off da Toshiba
  • Em 2019 renomeada para Kioxia
  • Chips pré-2019: marcados "Toshiba" físicamente no die
  • Chips pós-2019: marcados "Kioxia" — mas a numeração THGBM continua!
  • Na esteira de reciclagem aparecem ambas as gerações
  • No banco: registrar Brand separada para cada ("Toshiba" e "Kioxia")
    mas usando os mesmos DecodeMap onde a estrutura do PN for idêntica

FAMÍLIAS VISTAS NA ESTEIRA (ponto de partida):

  THGBM* — eMMC Mobile (família principal, ~2013-hoje)
    Exemplos reais:
      THGBM4G4D4LBAIR  (~4GB eMMC 4.41)
      THGBM5G6A4JBAIR  (~8GB?)
      THGBMHG8C4LBAIL  (~32GB eMMC 5.1)
      THGBMNG6JALAIG   (~16GB eMMC 5.1?)
      THGBMBG8D2KBAIG  (~32GB eMMC 5.1?)
    PN muito mais longo que Samsung (14-16+ chars vs 10 chars Samsung)
    A estrutura interna é MENOS documentada que Samsung — precisa brainstorm

  THGAF* — UFS Mobile (Toshiba, era 2016-2019)
    Exemplos: THGAF8G8T23BAIL (UFS 2.1), THGAF2G8T43BAIR
    Interface UFS — destino bancada uMCP/UFS

  KLUE* — UFS Mobile (Kioxia, 2020+)
    Exemplos: KLUEG8UHEC-B0C1, KLUEG4RHEC-B0C1
    Alta geração (UFS 3.1) — chips premium, alto valor

  TH58* — NAND Flash standalone (industrial/embutido, menos frequente)
    Menos relevante para a esteira de smartphones — baixa prioridade

4. BRAINSTORM NECESSÁRIO — ANATOMIA DO PN THGBM
════════════════════════════════════════════════════════════════════════

Esta é a principal tarefa: desvendar a estrutura posicional do THGBM.

Samsung tem estrutura bem documentada: posição fixa por tipo de info.
Toshiba/Kioxia é mais opaca. Precisamos descobrir:

  Posição 0-4: "THGBM" = prefixo fixo (Toshiba/Kioxia eMMC Mobile BGA)
  Posição 5:   ? (parece ser densidade ou geração — 4, 5, H, N, M, B...)
  Posição 6:   ? (talvez geração eMMC: 4=eMMC4.x, 5=eMMC5.x, G=?)
  Posição 7:   ? (possivelmente sub-capacidade ou revisão)
  ...

Método de brainstorm sugerido:
  1. Reunir 10-15 PNs THGBM com especificações conhecidas (via kioxia.com
     ou Octopart) — quantidade de GB + versão eMMC (4.x vs 5.1)
  2. Alinhar os PNs lado a lado por posição
  3. Identificar quais posições variam de forma correlacionada com GB
  4. Validar hipótese em pelo menos 3 PNs independentes antes de adicionar
     ao DecodeMap

Referências para pesquisa:
  • https://kioxia.com/global/en/product/flash-memory/emmc/
  • https://toshiba.semicon-storage.com/ap-en/semiconductor/product/flash-memory/emmc.html
  • Octopart: buscar "THGBM" com filtro Samsung/Kioxia
  • Preduo: preduo.com — distribuidor B2B com specs por PN
