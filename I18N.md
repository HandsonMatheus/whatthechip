# I18N.md — Internacionalização do WhatTheChip (WTC)

> Bíblia técnica do sistema de tradução do WTC. É o arquivo que o **chat
> especializado em i18n** mantém (análogo ao `RENTABILIDADE.md`, `FUZZY.md`,
> `MICRON.md`). Leia inteiro antes de mexer em tradução. Em conflito com este
> doc, **o código vence** (`core/settings.py`, `chips/labels.py`,
> `tenancy/middleware.py::UserLanguageMiddleware`,
> `chips/management/commands/check_translations.py`, os templates).
>
> **Status (2026-07-08): SISTEMA COMPLETO E NO AR — as 3 superfícies.** Quatro
> idiomas ativos — **pt-br** (fonte), **es**, **en**, **zh-hans** — cobrindo o
> site público **inclusive a HOME (CMS)**, a bancada/painel, o login e o
> dashboard do parceiro. Detecção por região (Accept-Language) + cookie +
> **preferência por usuário no banco** (editável na ficha do usuário no admin).
> Django admin **fixo em pt-br** (decisão §2.7). Portões: `check_translations`
> + `I18nChoicesDeclarationTests` + suíte (310 testes) verdes. Pendências
> menores no §10 (fila de conteúdo fab-*, tokenização do decode).

## 1. A tese: separar DADO de LÍNGUA

O WTC não é um site comum de traduzir — ele **gera texto**. Um chip decodificado
vira strings como `"8Gb = 1GB por die [✓]"`, `"LPDDR3 1GB"`, `"RENTÁVEL"`. Esse
texto mistura **dado** (capacidade, tipo) com **língua** (as palavras de ligação
e os veredictos). Traduzir bem = **separar as duas camadas**, exatamente como o
projeto já faz com `assess_profitability` (fonte única) e `canonical_gen`
(rótulo por whitelist).

Existem **três superfícies** de tradução, com estratégias diferentes:

| # | Superfície | Exemplos | Estratégia | Fase |
|---|---|---|---|---|
| **1** | **Chrome / UI** (site, bancada, painel, parceiro, login) | nav, botões, modais, gateway de triagem, mensagens de view, JS | `gettext` + `.po` (git) | ✅ **completa** |
| **2** | **Saída do engine** (dado+língua) | `RENTÁVEL`, `banco de dados`, `por die`, `consultar datasheet` | **chave canônica** (lógica) → **rótulo traduzido** (`chips/labels.py`) | ✅ vereditos/fontes · ⏳ tokenizar decode (§5.1) |
| **3** | **Conteúdo do CMS** | home, contato, páginas de fabricante | **arquivo por idioma** (`_content/<slug>.<código>.html`) + `django-modeltranslation` p/ metadados | ✅ mecanismo + home · ⏳ fila fab-* (§9) |

> **Regra de ouro do i18n:** na **lógica**, nunca compare contra o texto exibido.
> Compare contra o **valor canônico** (ou uma **chave** estável). O texto é só
> pixel. Vale para todo o sistema (armadilhas reais em §8).

## 2. Decisões de arquitetura (o porquê)

**2.1 — UI = `gettext` + `.po` versionado no git.** Padrão Django, casa com a
filosofia "conhecimento como código" e com a **regra de ouro #1** (o agente edita
arquivos; o dono roda os comandos). O `.po` é a fonte da verdade da tradução da
UI; o `.mo` compilado é o que o runtime lê. **Idioma novo ≈ 1 par de `.po`
traduzidos** — nada de migração, nada de engine.

**2.2 — Seleção de idioma = cookie/preferência via `LocaleMiddleware`**, **não**
`i18n_patterns` (prefixo de URL tipo `/es/...`). Motivo: a `core/urls.py` termina
numa rota **catch-all** `path('<slug:slug>/', ...)` que serve o CMS; `i18n_patterns`
envolve a URLconf raiz inteira e interage de forma delicada com esse catch-all.
Cookie não muda nenhuma URL e é zero-risco. **Upgrade futuro (SEO):** se as
páginas públicas precisarem de URL por idioma (indexar `/es/samsung`), migrar as
rotas de conteúdo para `i18n_patterns` — decisão à parte, com teste do catch-all.

**2.3 — "Região" = `Accept-Language`, NÃO GeoIP.** O requisito "ativa pela região
de quem acessa" é atendido pelo cabeçalho `Accept-Language` que todo navegador
envia (o idioma do sistema/navegador do usuário). É o padrão da web para
negociação de língua e é **melhor** que GeoIP: um comprador chinês viajando no
Paraguai continua vendo 中文; VPN não engana; não precisa de base GeoIP nem de
serviço externo. O Django resolve sozinho, inclusive variantes
(`zh-CN` → `zh-hans`, `es-PY` → `es`).

**2.4 — Preferência por USUÁRIO no banco (`tenancy.UserLanguage`).** Cookie é
por-navegador; a preferência é da **conta** e segue o usuário em qualquer
dispositivo. É **GLOBAL** (sem `company`): a língua é da pessoa, não da empresa —
um técnico chinês numa empresa paraguaia lê 中文 (declarada em
`estoque/tests.py::TenancyDeclarationTests`). O dono pode pré-configurar no admin
ao criar a conta (não há cadastro público); o usuário muda quando quiser pelo
seletor (que **persiste** a escolha — `tenancy/views.py::set_language`).

**2.5 — Conteúdo do CMS = ARQUIVO POR IDIOMA + `django-modeltranslation` para
metadados (implementado 2026-07-08).** Descoberta de implementação: as views de
`pages` leem o conteúdo **direto de `_content/<slug>.html` no disco** (o banco é
metadado + fallback) — então a tradução de conteúdo vive onde o conteúdo vive:
**`_content/<slug>.<código>.html`** (ex.: `index.es.html`), escolhido pelo
idioma ativo em `pages/views.py::_localized_content_path()`, com fallback
automático pro arquivo pt-br. Conteúdo-como-código: traduções versionadas no
git, revisáveis em PR, mesma rotina do §7. O `django-modeltranslation` cobre o
resto: **metadados** (`title`/`nav_title`/`section` — o `<title>` da aba) e
páginas criadas só no admin (sem arquivo). Colunas por idioma na mesma tabela,
PT na base, abas no admin, `MODELTRANSLATION_FALLBACK_LANGUAGES=('pt-br',)`.
Migrações `pages/0003` (colunas) + `0004` (backfill pt-br) — aditivas, rodam no
deploy. Alternativa `django-parler` descartada (mais invasiva, vantagem
marginal). Detalhes: §9.

**2.6 — Manutenção = rotina com agente/IA + PORTÃO (`check_translations`).**
O sistema ganha páginas todo dia; a rotina (§7) foi desenhada para um modelo
simples traduzir **sem poder errar**: o portão valida placeholders, HTML,
glossário e completude, e a publicação continua nas mãos do dono. Poedit/Weblate
continuam compatíveis (tudo é `.po` padrão) se um dia houver tradutores humanos.

**2.7 — Django admin = FIXO em pt-br (decisão do dono, 2026-07-08).** O admin é
superfície de **plataforma** (só o dono — T1); o chrome do Django traduz sozinho
mas nossos `verbose_name` são PT de propósito, e o híbrido parecia quebrado.
Fixar (pin no `UserLanguageMiddleware`, caminho `/admin/`) dá 100% de
consistência com **zero dívida** de tradução de admin (~300 strings que só o
dono veria). O APP inteiro continua multilíngue. Se um dia houver operador de
plataforma não-lusófono, reavaliar (basta remover o pin e marcar os
`verbose_name` — o custo fica documentado, não escondido).

**2.8 — Choices de modelo: rótulo exibido = `gettext_lazy`; resto = declarado.**
Classe de erro real (o crachá de papel do header ficava em PT nos 4 idiomas):
rótulo de choices que chega a usuário final tem que nascer com `_lazy`. O
**portão `I18nChoicesDeclarationTests`** (chips/tests_i18n.py) força a decisão:
todo campo com choices dos apps do projeto ou tem rótulos lazy, ou está na
lista `DECLARADOS` com justificativa (admin-only/rótulo-dado). Campo novo sem
decisão = suíte vermelha — mesmo padrão do `TenancyDeclarationTests`.

## 3. A CADEIA DE RESOLUÇÃO de idioma (como o sistema decide a língua)

Prioridade de cima pra baixo — a primeira camada que responde, vence:

```
1. UserLanguage (banco)   ← usuário LOGADO com preferência salva
      tenancy/middleware.py::UserLanguageMiddleware (depois do TenancyMiddleware)
2. Cookie django_language ← escolha no seletor (anônimo ou logado); dura 1 ano
      django.middleware.locale.LocaleMiddleware        (LANGUAGE_COOKIE_AGE)
3. Accept-Language        ← a "região": idioma do navegador do visitante
      django.middleware.locale.LocaleMiddleware
4. pt-br                  ← LANGUAGE_CODE (fallback e idioma-fonte)
```

Peças (tudo já no ar):

- **`core/settings.py`** — `LANGUAGES` = pt-br/es/en/zh-hans;
  `LOCALE_PATHS`; `LANGUAGE_COOKIE_AGE = 1 ano`; `LocaleMiddleware` (depois de
  `SessionMiddleware`, antes de `CommonMiddleware`) + `UserLanguageMiddleware`
  (depois de `AuthenticationMiddleware`/`TenancyMiddleware`).
- **`tenancy/models.py::UserLanguage`** — OneToOne com o User; `language` com
  choices **dinâmicos** = `settings.LANGUAGES` (callable, Django 5): idioma novo
  não pede migração. Vazio = automático. Admin em `tenancy/admin.py`.
- **`tenancy/middleware.py::UserLanguageMiddleware`** — ativa a preferência por
  cima do que o LocaleMiddleware decidiu. Fail-open: preferência inválida
  (idioma removido do settings) cai na detecção.
- **`tenancy/views.py::set_language`** — envolve a view nativa do Django
  (cookie + redirect) e, logado, **persiste** em `UserLanguage`. Mesma rota/nome
  (`{% url 'set_language' %}`) — os templates não sabem a diferença.
- **`core/urls.py`** — `i18n/setlang/` (a view acima) e `i18n/js/`
  (`JavaScriptCatalog`, ver §6.4). Ambas ANTES da rota catch-all `<slug>`.
- **Seletores de idioma** — 3 pontos: dropdown do topnav
  (`templates/base.html`, dirigido por `settings.LANGUAGES` — idioma novo aparece
  sozinho), e o **seletor compacto reutilizável**
  `templates/partials/lang_select.html` incluído no header do painel
  (`base_estoque.html`), no login e no header do parceiro (`partner_base.html`).

**Como testar na mão:** janela anônima com navegador em espanhol → site em ES
(camada 3). Trocar no seletor pra EN → cookie (camada 2). Logar com usuário que
tem preferência 中文 → tudo vira 中文 (camada 1), em qualquer máquina.

## 4. Como ADICIONAR UM IDIOMA (passo a passo)

Exemplo: adicionar francês (`fr`).

1. **`core/settings.py`** → adicione `('fr', _('Français'))` em `LANGUAGES`.
2. **Gere os catálogos** `locale/fr/LC_MESSAGES/django.po` + `djangojs.po`
   (§6.2 com gettext, ou §6.3 sem) e **traduza** (rotina §7).
3. **Compile** os `.mo` (§6.2/§6.3).
4. **`python manage.py check_translations --language fr`** → tem que passar.
5. Commit `.po` + `.mo` + settings. Deploy (§11).

Nenhuma mudança de engine, template, seletor ou migração — os seletores leem
`settings.LANGUAGES` e o modelo `UserLanguage` usa choices dinâmicos.
**Idioma novo ≈ 2 arquivos `.po` traduzidos.**

> Locale dir ≠ código: `zh-hans` (código) vive em `locale/zh_Hans/` (diretório,
> via `to_locale`). O `check_translations` já converte sozinho.

## 5. O desacoplamento do engine (superfície 2) — o coração do WTC

O engine é **lógica** e continua falando em **valores canônicos** (em português,
que dobram de `msgid`). Traduzir o retorno dele quebraria o sistema: o gateway do
estoque (`estoque/views.py`), o `is_dead_by_generation` e os testes **comparam
contra esses valores**.

| Papel | Exemplo | Onde | Traduz? |
|---|---|---|---|
| **valor canônico** | `"NÃO RENTÁVEL"`, `"banco de dados"` | retorno do engine | **NUNCA** — é chave de lógica |
| **chave** | `"nao-rentavel"`, `gateway_dest`, `step.status` | views/CSS | não — é lógica/estilo |
| **rótulo** | `"NOT PROFITABLE"`, `"数据库"` | `chips/labels.py` | **SIM** — só exibição |

**`chips/labels.py`** é a **fonte única** desses rótulos. Hoje: `profitability_label()`
(RENTÁVEL / NÃO RENTÁVEL / INDETERMINADO) e `source_label()` (gramática ·
gramática+db · banco de dados — o mesmo valor que `CONFIRMED_SOURCES` compara na
lógica do estoque, por isso o engine **não** muda). Ambos **fail-open**: valor
desconhecido volta cru. Views passam o rótulo ao template
(`profitable_label`, `classification_source_label`); a lógica de template usa
`profitable_key`/`gateway_dest`.

O mesmo padrão nos dicts de view: `_CONF_LABEL` (chips/views.py) e os
`steps[].label/detail` do gateway (estoque/views.py) têm **chave canônica +
rótulo gettext**. Strings **persistidas** ficam canônicas — ver §8.2.

### 5.1 — Fase 2: tokenizar o vocabulário de decode (ainda pendente)

O engine embute palavras de ligação PT **dentro** das strings compostas:
`"8Gb = 1GB por die [✓]"`, `"tipo 'X' — consultar datasheet ⚠ cap. não mapeada"`,
`"Código 'X' não mapeado"`. E o `DecodeMap.val_secondary = "por die"` guarda
português **no dado** (regra de ouro #4). Traduzir isso exige **tokenizar**: o
engine emite campos estruturados + códigos de estado, e a apresentação monta a
frase com conectivos traduzidos. É refactor cirúrgico e de risco (mexe em
snapshot do estoque e no `DecodeMap`) → **fase 2**, com rede de testes própria.
Vocabulário fechado a mapear: `por die`, `consultar datasheet`, `não mapeada`,
`não mapeado`, `cap. não mapeada`, `RAM não mapeada`, `tipo`,
`sem documentação pública`, `estimativas por analogia estrutural`.
Até lá: esses fragmentos aparecem em PT dentro do card em qualquer idioma —
são quase todos specs técnicos, legíveis pelo operador.

## 6. Como MARCAR strings e gerar/compilar catálogos

### 6.1 — Marcar (o padrão)

**Templates** (precisa `{% load i18n %}` no topo):
```django
{% trans "Texto simples" %}
{% blocktrans trimmed %}Texto com {{ variavel }} dentro{% endblocktrans %}
```
- **`trimmed`** sempre no `blocktrans` — sem ele a indentação entra no `msgid`.
- Emojis/símbolos **fora** do `trans` (`⚠ {% trans "..." %}`).
- Variável com filtro: `{% blocktrans trimmed with n=lot.number|stringformat:"03d" %}`.
- Atributos: `placeholder="{% trans 'Filtrar por PN…' %}"` (aspas alternadas).
- **JS inline** (dentro de `<script>` no template): o template renderiza o JS —
  use `'{% trans "Texto" %}'` no literal. String com apóstrofo no conteúdo:
  reescreva sem, ou mova pro catálogo JS (§6.4).

**Python** (views, labels, choices exibidos):
```python
from django.utils.translation import gettext as _          # eager: dentro de view
from django.utils.translation import gettext_lazy as _lazy  # lazy: módulo/modelo/choices
```
Dict de módulo (ex.: `_CONF_LABEL`) = lazy. Mensagem dentro de view = eager.
⚠ Não ponha proxy lazy em `json.dumps` — em `JsonResponse` de view use eager.

**O que NUNCA marcar:** PNs, specs (`LPDDR4`, `x16`, `8Gb`), códigos de caixa
(`{{ destination }}`, `EMCP16+1`), marcas, valores comparados em `{% if %}`,
`value=` de hidden, chaves de dict, classes CSS, strings persistidas (§8.2),
o `WORD_MAP` fonético do mic.js (é dado de ditado, não língua).

### 6.2 — Gerar / compilar COM gettext (o fluxo canônico — máquina do dono)

```bash
brew install gettext                                   # 1ª vez no macOS
python manage.py makemessages -l es -l en -l zh_Hans -i venv -i staticfiles
python manage.py makemessages -d djangojs -l es -l en -l zh_Hans -i venv -i staticfiles -i node_modules
#   … traduzir os .po (rotina §7) …
python manage.py compilemessages
python manage.py check_translations                    # o portão — tem que passar
```
`makemessages` é aditivo/idempotente: re-rodar faz `msgmerge`, preserva traduções
existentes e marca `#, fuzzy` o que mudou (fuzzy NÃO some sozinho — é revisão).

### 6.3 — Gerar / compilar SEM gettext (sandbox de agente)

Dois utilitários versionados cobrem o ambiente sem `xgettext`/`msgfmt`:

```bash
python scripts/i18n_extract.py > /tmp/msgids.json   # extrai msgids (mesmo templatize do makemessages)
python scripts/i18n_compile.py                      # compila locale/**/*.po → .mo (polib)
```
A extração vive na biblioteca **`chips/i18n_source.py`** (o script é um CLI
fino sobre ela) — a MESMA que o `check_translations` usa na regra 8, então
"o que se extrai" e "o que o portão cobra" nunca divergem. Descobre apps/
templates dinamicamente (app novo entra sozinho) e anota as localizações
`#: arquivo:linha` de cada msgid (rastreabilidade nos .po). Produz msgids
idênticos aos do makemessages (msgmerge-compatível). `i18n_compile.py` exige
`polib` (está no `requirements.txt`). A ESCRITA do `.po` em si o agente faz
diretamente (é texto) — e o `check_translations` valida antes de qualquer commit.

### 6.4 — JavaScript ESTÁTICO (`static/js/*.js`)

`{% trans %}` não alcança arquivo `.js` servido estático. O caminho é o
**`JavaScriptCatalog`** (já ligado): a rota `i18n/js/` serve `window.gettext()`
no idioma ativo, e os bases incluem `<script src="{% url 'javascript-catalog' %}">`
**antes** do `mic.js`. No `.js`, envolva com `gettext('…')` (o `mic.js` tem um
shim fail-open no topo — sem catálogo, devolve o pt-br). Esses msgids vivem no
domínio **`djangojs`** (`djangojs.po`), extraídos com `makemessages -d djangojs`
(ou o `i18n_extract.py`).

## 7. A ROTINA DE TRADUÇÃO (segura para um modelo de IA simples)

> O sistema ganha páginas todos os dias. Esta rotina existe para que a tradução
> acompanhe SEM abrir espaço para erro: o tradutor (humano ou **modelo de IA
> simples**) trabalha **preso entre dois portões** — as regras abaixo na
> entrada, e o `check_translations` + revisão do dono na saída. O modelo só
> preenche `msgstr`; ele **não decide** nada estrutural.

### 7.1 — O contrato do tradutor (as regras invioláveis)

1. **Traduza SÓ o `msgstr`.** `msgid`, comentários, flags, ordem e metadados são
   intocáveis. Nunca adicione nem remova entradas.
2. **Placeholders são sagrados.** Todo `%(nome)s`, `%s`, `%d`, `{nome}` e `%%`
   do msgid reaparece IDÊNTICO (mesmo nome, mesma quantidade) no msgstr — pode
   mudar de posição na frase, nunca de grafia.
3. **HTML é sagrado.** Tags (`<strong>`, `<em>`, `<code>`, `<br>`) e entidades
   (`&nbsp;`) do msgid reaparecem idênticas, na mesma ordem, envolvendo o trecho
   equivalente.
4. **Glossário DO-NOT-TRANSLATE** (fonte única: `PROTECTED_TERMS` em
   `chips/management/commands/check_translations.py`): `WhatTheChip`,
   `Part Number`, `PN`, `FBGA`, `eMCP`, `uMCP`, `eMMC`, `UFS`, `LPDDR`, `DDR`,
   `GDDR`, `NAND`, `US$`, `USD`, `Octopart`, `datasheet`, nomes de marca
   (`Samsung`, `SK Hynix`, `Micron`…), `Enter`. Ficam **intactos, no alfabeto
   latino, em qualquer idioma** (inclusive 中文 — o operador vê "Samsung"
   gravado no chip e nas tags da UI; consistência vence naturalidade).
5. **Emojis e símbolos** (✅ ✏️ 🏪 📐 ⚠ ✓ ✗ →) que estiverem no msgid ficam no
   msgstr, na mesma posição relativa.
6. **Espaços de borda e quebras de linha** do msgid se preservam no msgstr
   (fragmentos concatenam em template/JS — espaço perdido = palavras coladas).
7. **Vereditos e termos de triagem usam a tradução CONSAGRADA** (consistência >
   criatividade): consulte os catálogos existentes antes de inventar termo novo.
   Ex.: RENTÁVEL = `RENTABLE`/`PROFITABLE`/`有利润`; fila de conferência =
   `cola de verificación`/`review queue`/`复核队列`; lote = `lote`/`lot`/`批次`.
8. **Em dúvida → fuzzy, nunca chute.** Termo ambíguo, contexto insuficiente,
   possível dado técnico: marque `#, fuzzy` e anote a dúvida para o dono. O
   portão barra fuzzy de ir pra produção — é o mecanismo certo de "não sei".
9. **Registro:** es = tuteo latino-americano (público Paraguai); en = técnico e
   conciso; zh-hans = 简体, registro técnico de bancada.

### 7.2 — O passo a passo da rotina (a cada leva de strings novas)

```
1. EXTRAIR    makemessages (§6.2) ou i18n_extract.py (§6.3)
              → entradas novas aparecem com msgstr vazio; alteradas viram fuzzy
2. TRADUZIR   o modelo preenche APENAS os msgstr vazios/fuzzy, sob o contrato §7.1
3. COMPILAR   compilemessages ou scripts/i18n_compile.py
4. PORTÃO     python manage.py check_translations        ← exit ≠ 0 = NÃO PUBLICA
5. SUÍTE      python manage.py test chips estoque --settings=core.settings_test
              (inclui chips/tests_i18n.py: cadeia, rótulos, smoke nos 4 idiomas)
6. REVISÃO    dono olha o diff dos .po (as entradas novas são poucas por leva)
7. COMMIT     .po + .mo juntos → push → deploy (§11)
```

### 7.3 — O que o portão barra (classe de erro → trava)

| Classe de erro do tradutor | Trava que pega |
|---|---|
| idioma ativado sem catálogo | `check_translations` regra 1 |
| entrada esquecida (msgstr vazio) / fuzzy remanescente | regra 2 |
| placeholder renomeado/perdido (`%(qty)s`→`%(cantidad)s`) | regra 3 |
| tag/entidade HTML perdida (`<strong>` sumiu, `&nbsp;`→espaço) | regra 4 |
| termo protegido traduzido (`Part Number`→`Número de pieza`) | regra 5 (glossário) |
| espaço de borda perdido (fragmento JS cola na variável) | regra 6 |
| `.mo` esquecido/desatualizado (tradução "não aparece") | regra 7 |
| valor canônico traduzido na lógica | `chips/tests_i18n.py::test_valor_canonico_nunca_muda` + suíte |
| template quebrado pela marcação | smoke tests nos 4 idiomas + suíte |
| choices de modelo exibido sem `gettext_lazy` | `I18nChoicesDeclarationTests` (§2.8) |
| placeholder `{{STAT_*}}`/`{{PREFIX_DATA}}` quebrado em conteúdo traduzido | `test_home_placeholders_resolvem_em_todo_idioma` |
| idioma do usuário "vazando" pro Django admin | `AdminPlataformaPtBrTests` (§2.7) |
| **string MARCADA mas não traduzida** (chat "esqueceu" a rotina) | `check_translations` **regra 8** — completude código→catálogos, via `chips/i18n_source.py` (descoberta dinâmica de apps; erro com `arquivo:linha`) |
| **texto PT CRU no template** (nem marcou) | `check_translations` **regra 9** — detector por diacrítico fora de `{% trans %}`; exceção deliberada = comentário `i18n-ok` NA LINHA (ex.: dump de debug do estoque) |

Como a suíte roda o portão (`PortaoDeCatalogoTests`), **quebrar o contrato =
suíte vermelha** — a imposição não depende de obediência (pilha completa:
MULTILANGUAGE.md §7.3). O que segue não-automatizável — e por isso a revisão
do dono continua no fluxo: frase PT **sem nenhum acento** (raro) e tradução
gramaticalmente correta porém **errada de sentido**. Mesma filosofia do
catálogo: a máquina trava a estrutura, o humano é o filtro final de veracidade.

## 8. Armadilhas (o que quebra o i18n)

**8.1 — Comparar contra literal PT na lógica (a landmine principal).** O
`decode_card.html` fazia `{% if profitable == "RENTÁVEL" %}` — corrigido para
`profitable_key`. O mesmo padrão foi respeitado em TODA a marcação: `gateway_dest`,
`step.status`, `lot.status` são chaves e ficaram intocados. **Regra:** ao marcar
uma string que também é comparada, troque a comparação pela **chave**. Varra
`grep -rn "== '" templates/ */templates/` antes de traduzir bloco novo.

**8.2 — String PERSISTIDA fica canônica (pt-br), sempre.** O que vai pro banco é
DADO/auditoria, não exibição: `RejectedEntry.rejection_reason`
(`'NÃO RENTÁVEL (geração)'` — comentado no código com ⚠ CANÔNICO), labels de
caixa (`EMCP16+1`), snapshot do estoque, cabeçalhos do `export_xls` (planilha
que circula com o comprador — layout fixo). Traduzir na gravação faria o dado
depender do idioma de quem operou (linhas históricas em 4 línguas misturadas).
Solução futura para exibir traduzido: rótulo **on-read** (chave → label), fase 2.

**8.3 — `DecodeMap.val_secondary = "por die"`** guarda PT no dado (regra de ouro
#4). Faz parte da tokenização da §5.1 — **não** traduza o `DecodeMap` no braço.

**8.4 — JS:** inline usa `{% trans %}`; estático usa `JavaScriptCatalog` (§6.4).
Não esqueça o `<script src="{% url 'javascript-catalog' %}">` ANTES do `.js` que
usa `gettext()` (os dois bases já têm). String JS ao mesmo tempo atribuída E
comparada → não marque.

**8.5 — `verbose_name`/`help_text` dos modelos** ficam em PT cru **de propósito**:
o Django admin é ferramenta de PLATAFORMA (só o dono — T1) e o dono opera em PT.
Exceção já tratada: choices **exibidos a usuário final** (STATUS/REVIEW do
pricing, no /partner/) passam por `gettext_lazy`. Se um dia o admin virar
multilíngue, marcar com `gettext_lazy` (lazy: roda no import).

**8.6 — `.mo` ausente/velho em produção.** O runtime lê o `.mo`, não o `.po`.
Sem compilar+commitar, o idioma **não aparece** (fallback silencioso pro PT).
O `check_translations` (regra 7) pega isso antes do commit.

**8.7 — Não marque PN/códigos/specs.** `KM3V6001CM`, `LPDDR4`, `x16`, `8Gb` são
dados. O `WORD_MAP` do mic.js (fonética de ditado) também é dado.

**8.8 — Cache de página × idioma.** `cache_page` num view traduzido serviria o
HTML do primeiro idioma a todo mundo. Hoje NENHUMA view traduzida usa cache
(o import de `cache_page` em chips/views.py está órfão). Se um dia cachear:
`Vary: Accept-Language` + chave por idioma.

**8.9 — Lazy proxy fora de template.** `gettext_lazy` em `json.dumps` estoura
`TypeError`. Em `JsonResponse` de view, use `gettext` (eager) — resolve no
idioma da request na hora.

## 9. Conteúdo do CMS (superfície 3) — IMPLEMENTADO (2026-07-08)

**O desenho real (files-first):** as views de `pages` leem o conteúdo direto de
`_content/` no disco; o banco guarda metadados + fallback. A tradução segue a
mesma geografia:

```
_content/index.html            ← pt-br (fonte + fallback universal)
_content/index.es.html         ← tradução ES   ┐ escolhidos por
_content/index.en.html         ← tradução EN   ├ _localized_content_path()
_content/index.zh-hans.html    ← tradução 中文  ┘ (idioma ativo; pages/views.py)
```

- **Conteúdo** = arquivo por idioma no git (conteúdo-como-código; PR revisável;
  produzido pela rotina do §7 — na home, gerado por tabela de substituição
  exata que preserva markup/JS/placeholders `{{STAT_*}}`/`{{PREFIX_DATA}}`).
  Sem arquivo traduzido → o slug cai no arquivo pt-br. **Nunca em branco.**
- **Metadados** (`title`/`nav_title`/`section` — o `<title>` da aba, navegação)
  = `django-modeltranslation` (colunas `title_es`… na própria tabela; abas no
  admin via `TranslationAdmin`). Carregados pelo `import_content` (chave
  `'i18n'` por página — index/fabricantes/contato já têm; `2.1 Samsung` etc.
  não precisam: nome de marca é igual em todo idioma).
- **Páginas só-admin** (sem arquivo em `_content/`): o conteúdo do banco também
  tem colunas por idioma — o admin resolve, com fallback pt-br.
- Migrações: `pages/0003` (colunas, gerada) + `0004` (backfill do PT existente
  para as colunas `*_pt_br` — sem isso o fallback acharia NULL). Aditivas,
  rodam sozinhas no deploy.

**Regra de manutenção (a staleness é humana, não mágica):** editou o
`_content/<slug>.html` (PT)? **Atualize os `<slug>.<código>.html` na MESMA
sessão** (rotina §7). Esqueceu? O usuário estrangeiro vê a versão antiga do
trecho — nunca uma página quebrada. O diff do git denuncia (arquivo PT mudou
sem os irmãos mudarem).

**Fila de conteúdo pendente** (fallback PT até traduzir): `fabricantes`,
`fab-samsung` … `fab-gigadevice`, `contato` — traduzir sob demanda de mercado,
começando pelas marcas que o público-alvo consulta (decisão de negócio).

## 11. Deploy (Render)

O runtime lê `locale/<locale>/LC_MESSAGES/*.mo`. Estratégia vigente:
**(A) commitar `.po` + `.mo` juntos** (o `.gitignore` não os ignora) — zero
fricção, o Render não precisa de gettext. Alternativa (B): `compilemessages` no
Build Command — exige gettext na imagem de build; migrar quando o volume de
idiomas justificar. **Não** depende de `catalog_version` (aquilo é
gramática/known_parts) nem de `collectstatic` (o `.mo` não é estático) — reflete
no deploy seguinte ao push.

**A migração `tenancy/0003_userlanguage` roda no build** (migrations aditivas,
padrão do projeto). Checklist de publicação de i18n:

```bash
python manage.py check_translations          # portão verde
python manage.py test chips estoque --settings=core.settings_test
git add locale/ core/settings.py …           # .po + .mo JUNTOS
git push origin main                          # Render: migrate + deploy
```
